知识库智能体01 · 业务背景
先对齐问题。我们手里有约 1000 份 PDF，主要是三类：数据产品接口文档和产品介绍、公司流程制度、数据表字段说明。这几类的共同特点是表格密集、结构化强、充满精确术语——比如字段名、流程编号、接口参数。使用者是业务人员，他们不会写代码，要用大白话提问就能查到答案，而且答案必须带来源引用。技术上，检索要由 Agent 自主规划，能多跳查、能自己判断要不要重试，不是固定流水线。部署全自托管，LLM 走公司内部端点。最后强调一点：这个 Agent 只做查询检索，绝不执行任何写操作或调外部系统。

传统 RAG 在我们的场景下有三个致命伤

偏差大
💧

知识不沉淀

每次查询都从原文临时重新发现知识，无积累。两份文档同字段不同值，向量库不会告诉你。

无自愈

阿里云 2026 测试显示：Dify 等工作流平台在表格 / 结构化文档上准确率低，主因正是切片 + 弱检索。

知识库智能体01 · 业务背景
这是选型的出发点。很多人想到知识库就是 RAG，就是向量检索加 LLM。但传统 RAG 在我们这种表格密集的结构化内部文档上有三个致命伤。第一，切片会切断上下文：表格的表头和数据行被切到不同 chunk，接口文档字段说明和示例分离，表格文档首当其冲。第二，语义漂移：业务人员用口语问"接口怎么调"，文档里写的是"调用方法"，向量召回对不齐。第三，也是最根本的，知识不沉淀——每次查询都从原文临时重新发现，没有积累；两份文档说同一字段不同值，向量库根本不会提醒你矛盾。阿里云 2026 年的测试也印证了，工作流平台在表格文档上准确率低，主因就是切片加弱检索。所以我们不能简单照搬传统 RAG。

Key Insight · 先理清一个认知

检索方式 ≠ 检索架构

2026 年共识：RAG 是一个设计空间，不是单一模式。两个正交维度切分：

① 检索底座 —— 去哪找

向量库 关键词索引 知识图谱 文件系统目录 多模态视觉 长上下文全量

决定"数据存在哪里、靠什么召回"。

② 检索控制 —— 怎么找

静态流水线 Self-RAG 反思 CRAG 纠错 Adaptive 路由 Agent 自主规划

决定"检索到的东西要不要信、要不要再找"。

我们的需求 = 文件系统目录底座 × Agent 自主规划控制，两者是组合关系。

知识库智能体02 · 方案全集
这是整个汇报最关键的一个认知框架。很多人把 RAG 等同于"向量检索加 LLM"，这是 2023 年的认知。2026 年的共识是 RAG 是一个设计空间，不是单一模式。检索方案可以从两个正交维度切：一是检索底座，解决"去哪找"，包括向量库、关键词索引、知识图谱、文件系统目录、多模态视觉、长上下文全量；二是检索控制，解决"怎么找、要不要信、要不要再找"，包括静态流水线、Self-RAG 反思、CRAG 纠错、Adaptive 路由、Agent 自主规划。我们的需求落在哪？底座选文件系统目录，就是按目录分类加按需加载原文；控制选 Agent 自主规划，就是多跳加自评重试。这两个维度是组合关系，所以下面我会分两块展开，先过 7 种底座。

第一个方案，向量检索，就是大家最熟悉的传统 RAG。流程是文档切块、过 embedding 模型生成向量、存进向量库、查询时算余弦相似度做 Top-K 召回、再交给 LLM 生成。它的优点是成熟、适合语义模糊查询、能扩展到超大语料。但致命缺陷恰好命中我们的痛点：切片会切断表格的表头和数据行；业务口语和文档术语对不上时召回漂移；维护层面知识不沉淀，embedding 模型一升级还要全量重算。结论是：它不适合作为我们这种表格密集结构化文档的唯一底座。注意是"唯一底座"——后面会看到它还可以作为辅助。

第二个方案，关键词检索，也就是 BM25。原理是建倒排索引，查询时按 TF-IDF 打分做精确词项匹配。它最大的优点是精确、可解释、零训练成本，对字段名、流程编号、专有名词这种精确术语命中精准。2026 年实测在精确术语匹配数据集上达到 99.97%。而且索引是纯数据结构，坏了能从原文 100% 重建，没有模型漂移问题。缺陷是不理解同义词和 paraphrase，纯 BM25 在语义模糊查询上召回不足。所以它通常作为混合检索的一路，不单独用。对我们来说，接口文档字段名、数据表列名、流程编号这些精确术语场景，BM25 正好用得上。

第三个方案，混合检索加重排序，这是 2026 年的工程标配。思路是 BM25 稀疏召回管精确术语，向量稠密召回管语义模糊，两路用 RRF 即排名倒数加权融合，再用 Cross-Encoder 精排。优点是兼顾精确和语义，NDCG@3 提升约 22 个点。但缺陷是它仍然是切片范式，没解决表格被切断的问题；而且要维护两套索引加一个 reranker，运维复杂度高，还有两套索引一致性、幽灵命中的风险。它的定位是作为 Agent 的一个工具——给 Agent 提供高质量候选，而不是全局底座。

方案 4-7 · 其余三类底座

为什么不作为我们的主底座

GraphRAG

⭐ 契合度低

原理：LLM 抽实体/关系建图 → 子图遍历多跳推理。

强项：多跳关系推理最强（67%→94%）。

不适用：需数周本体建模；1000 份 ROI 极低；文档关系扁平，图谱优势发挥不出来。

P3 远期可选

多模态 ColPali

本项目不采用

原理：PDF 整页渲染成图 → VLM 生成 patch 多向量 → 跳过 OCR/切片。

强项：保留表格/图表版式空间关系。

不适用：本项目文档不含图片，无 VLM/GPU/多向量库需求。

仅完整性保留

长上下文全量

非独立

原理：1M-2M token 窗口，相关文档全文塞进 prompt。

强项：零切片损失、全文上下文完整。

定位：不是独立方案，是方案 6 的执行手段——Agent 加载的文档进长上下文推理。

配合方案 6

剩下三类底座一起说，重点是不作为主底座的理由。GraphRAG 多跳关系推理最强，从 67% 到 94%，但需要数周本体建模，1000 份文档 ROI 极低，而且我们的文档关系相对扁平，图谱优势发挥不出来，只能列为 P3 远期可选。多模态 ColPali 技术很先进，整页渲染成图、跳过 OCR、保留版式，但我们项目文档不含图片，所以不采用，只是保留完整性。长上下文全量注入，靠现代 LLM 的 1M 到 2M token 窗口全文塞进去，零切片损失，但它不是独立方案，是方案 6 的执行手段——Agent 按需加载的文档正好进长上下文窗口推理，两者天然组合。

这是我们的主方案，重点讲。思路是不给 Agent 配向量库，而是给一组文件系统导航工具：list_categories 浏览目录、list_documents 列候选文档、grep_docs 做 BM25 精确召回、read_section 按需加载原文段、grade_relevance 自评相关性，不达标就改写重检。Agent 自己决定调什么、何时调、调几次。结合现有代码说：L1 层已经落地了——M1 清洗把 PDF、Word、Excel 转成 markdown，Excel 还原成完整 markdown 表；M2 是两步 LLM 摄入，第一步抽取实体、概念、流程、摘要、关键词，第二步生成 wiki 目录树下的 sources、entities、concepts、process 四类页面，每页带 frontmatter，related 字段记录关联页面；再确定性生成 index.md 内容目录和 append-only 的 log.md 变更日志；检索用 rank-bm25 做 BM25，RRF k=60 融合，snippet 按行号切片最多 500 字，经 kb search 命令验证。五个 L2 工具里 grep_docs 已经由这套检索栈支撑，read_section 有行号切片原语，list_categories、list_documents 和 REST 服务是 M3 的事。实测背书很硬：Claude Code、Cursor、Devin 全用这个模式，FinanceBench 表格密集文档 agentic 关键词 30.40% 反超向量 RAG 的 24.24%，Vercel 加文件系统工具后砍掉 80% 专用工具准确率反升。一句话：这正是我们的场景——1000 份结构化内部文档、按目录分类、多跳自评。

控制层主选 · Agentic RAG (RAG + Agent) — 我们的控制方式

片段检索 + 单篇全读 + 多次查询，比工作流单次检索更准

把 RAG 从"一次性流水线"升级为"Agent 自主迭代的检索循环"。

🔍 片段检索（grep_docs）

  • BM25 关键词召回 → 返回 doc_id + section_id + snippet
  • snippet 按行号切片（≤500 字），是片段，不是全文
  • 低 token 成本、快速定位候选章节

📖 单篇内容全部检索（read_section）

  • 定位后 read_section 加载该章节完整原文
  • 表头与数据行、字段说明与示例不再被切断
  • "检索也是片段，但 Agent 可按需取全"——片段定位 + 全文理解

⭐ 多次查询 > 工作流单次检索

工作流 RAG：检索一次 → 拼上下文 → 生成，召回不全就答错，无补救 Agentic RAG：grade_relevance 自评 → 不达标则改写查询 / 换文档 / 再 grep，多跳迭代直至取全

本质区别：单次检索的召回上限即答案上限；Agent 多跳把"召回率"从一次的概率事件变成可迭代收敛的确定过程——这正是我们"基于 Agent 非工作流"硬约束的技术内核。

这一页讲我们的控制层主选——Agentic RAG，也就是 RAG 加 Agent。把 RAG 从一次性流水线升级成 Agent 自主迭代的检索循环。两个检索粒度：一是片段检索，grep_docs 走 BM25 召回，返回文档 id、章节 id、snippet，snippet 按行号切片最多 500 字，它是片段不是全文，低 token 成本快速定位候选。二是单篇内容全部检索，read_section 在定位后加载该章节完整原文，表头和数据行、字段说明和示例不再被切断。关键点：检索返回的也是片段，但 Agent 可以按需取全，片段定位加全文理解。最重要的一句——多次查询比工作流单次检索更准。工作流 RAG 是检索一次、拼上下文、生成，召回不全就答错，没有补救；Agentic RAG 是 grade_relevance 自评，不达标就改写查询、换文档、再 grep，多跳迭代直到取全。本质区别：单次检索的召回上限就是答案上限；Agent 多跳把召回率从一次的概率事件变成可迭代收敛的确定过程。这正是我们基于 Agent 非工作流这条硬约束的技术内核。

思想源头 · Karpathy LLM Wiki 方法论 (2026)

知识编译一次、持续更新，而非每次重新推导

核心理念：让 LLM 增量构建并维护一个持久化 Wiki——它是一个会复利的产物。

🏛️

三层架构

原始资料（只读）→ Wiki（LLM 生成的 markdown）→ Schema（CLAUDE.md，告诉 LLM 怎么干）

⚙️

三大操作

Ingest 投入资料→抽取更新页面 · Query 提问→带引用回答 · Lint 定期健康检查找矛盾/缺口

🧑‍💻

角色分工

人类负责策展来源、提问、判断方向；LLM 负责所有枯燥的维护工作——不嫌烦、不会忘、能一次改 15 个文件

关键洞察：index.md 在中等规模（~100 份来源）"出奇地好用"，可以完全不需要 embedding RAG 基础设施——印证了我们"按目录分类 + 按需加载原文"的直觉。

🏗️ 建设原理

  • 三层编译：raw → wiki → schema，原始只读、Wiki 由 LLM 生成、Schema(CLAUDE.md) 约束结构
  • Ingest 六步：投入资料 → 检索相关页 → LLM 抽取更新 → 写回页面 → 更新 [[wikilink]] → 刷新 index.md
  • 结构化沉淀：实体/概念/流程分目录 + frontmatter，一次编译、持续复用
  • "编译一次而非每次重推"——与传统 RAG 每次从原文临时召回的本质区别

🔁 维护理念

  • 角色分工：人类策展来源/方向，LLM 包揽枯燥维护——不嫌烦、不遗忘、一次改 15 个文件
  • Lint 混合体系：确定性检查（断裂 wikilink、孤儿页、frontmatter 缺失）+ LLM 语义检查（矛盾、过时、缺口）
  • 答案回填复利：Query 答完把结论回填进 wiki，新知识持续累积，越用越准
  • 维护成本近零：无模型漂移、无 embedding 重算，坏了从原文 100% 重建
知识库智能体03 · Karpathy 理念
Karpathy 是前 Tesla AI 总监、OpenAI 创始成员，2026 年发表了 LLM Wiki 方法论。核心理念一句话：传统 RAG 每次查询都从原文临时重新发现知识，没有积累；他主张让 LLM 增量构建并维护一个持久化 Wiki，知识编译一次、持续更新，Wiki 是个会复利的产物。三个关键设计：三层架构、三大操作、角色分工。最重要的洞察是 index.md 在中等规模出奇地好用，可以完全不需要 embedding RAG 基础设施，正好印证了我们按目录分类加按需加载原文的直觉。下半页展开两块。建设原理：三层编译 raw 到 wiki 到 schema，Ingest 六步——投入资料、检索相关页、LLM 抽取更新、写回页面、更新 wikilink、刷新 index.md，实体概念流程分目录加 frontmatter 做结构化沉淀，核心是编译一次而非每次重推。维护理念：角色分工人类策展 LLM 维护；Lint 是混合体系，确定性检查断裂链接孤儿页 frontmatter 缺失，LLM 做语义检查找矛盾过时缺口；答案回填复利，Query 答完把结论回填进 wiki，越用越准；维护成本近零，无模型漂移无 embedding 重算，坏了从原文 100% 重建。这两块正是我们 L1 摄入 pipeline 和 log.md/index.md 的思想源头。
